# 织光 WeaveMind V0.5 优化计划

> 版本：V0.5 ｜ 制定日期：2026-08-16 ｜ 依据：`标准/`（阿里云大模型 ACP 认证课程方法论）+ 全功能代码审计
>
> 原则：先安全与评测地基（P0），再能力闭环（P1），最后生产化（P2）。每条优化项均可独立验收、可回滚。

## 优先级说明

| 级别 | 含义 | 完成条件 |
|------|------|---------|
| P0 | 上线前必须修复：安全/合规/评测地基 | 有安全测试与评测集回归 |
| P1 | 核心能力闭环：Skill/记忆治理/验证器/评测驱动 | 对应能力有评测与回归 |
| P2 | 生产化增强：成本/性能/可观测性/工程规范 | 有量化指标与看板 |

## 二、详细优化表

### P0 安全与评测地基

| 编号 | 优化项 | 标准依据 | 现状/问题 | 具体修改动作 | 验收标准 |
|------|--------|---------|-----------|-------------|---------|
| O-01 | code_execution 沙箱隔离 | C4-4.4 指令注入 | 直接 `subprocess.run`，任务可执行任意命令/读任意文件 | 为 code_execution 增加容器沙箱（`--network none`、只读系统盘、仅挂载任务工作区、CPU/内存限额）；无容器环境时降级为受限令牌 + 命令白名单 | 恶意样例（读系统文件、外联、删库）全部被拦截；正常任务全量回归通过 |
| O-02 | 密钥与配置文件治理 | C1 环境准备 / C4-4.4 | `config.json` 明文存 key 且未被 gitignore；.env 可能入库 | `config.json`/`.env` 加入 .gitignore；改用环境变量或 Docker secrets；轮换已暴露的 API key | `git ls-files` 不含任何密钥文件；CI 密钥扫描通过 |
| O-03 | 输入输出内容安全与注入防护 | C4-4.4 提示词注入/内容安全 | 任务 goal/context 无长度上限、无审查、无注入检测 | ① goal 长度上限+限流；② `_dispatch` 前注入检测（规则+LLM 分类器）；③ 检索结果过滤危险内容/混淆；④ 输出侧（报告发布前）内容安全检测 | 注入样例（忽略指令/角色扮演/SQL 注入）拦截率 100%；违规内容输出被拦截 |
| O-04 | 知识库访问控制 | C4-4.4 / course_core kb_filter | 无企业知识库问答，若接入则无权限模型 | 参照 `kb_filter.py`：检索结果按用户职位白名单过滤，CSV/DB 存 用户-职位-文档 关系 | 越权文档不可见；权限矩阵测试通过 |
| O-05 | 建立评测集 evals/ | C2-2.4 / C3-3.6 专家 Ground Truth | 无答案质量评测集 | 新建 `evals/`：5 类任务各 3-5 条（调研报告/数据管道/游戏/文件操作/图表），含 goal、期望交付、关键内容点、rubric | 评测集可被 `python -m evals.run` 一键执行 |
| O-06 | 接入 Ragas 答案质量指标 | C2-2.4 Ragas | 只有过程评测（critic/反思/贯通测试），无答案质量评测 | 对报告/调研类任务跑 answer_correctness / faithfulness / context_recall / context_precision（复用 `标准/course_core/ragas_prompt/chinese_prompt.py` 中文提示词） | 每类任务产出 4 项指标分数并入库；分数随改进可对比 |

### P1 核心能力闭环

| 编号 | 优化项 | 标准依据 | 现状/问题 | 具体修改动作 | 验收标准 |
|------|--------|---------|-----------|-------------|---------|
| O-07 | Planner 步骤强制“验收点” | C3-3.2 Plan & Execute | 计划对题但执行可能跑偏 | PLANNER_SYSTEM 规则追加“instruction 必须以『验收：…』结尾”；`_normalize_steps` 缺失时自动补 | 抽查 10 个计划，100% 步骤含可验证验收点 |
| O-08 | 工作流编排模式 | C3-3.2 五种编排模式 | 只有并行 DAG + 串行反思 | 计划 JSON 支持 `mode: pipeline/parallel/human_in_loop`；人机协作任务生成步骤级人工确认点 | 三类模式各有一条任务按预期执行 |
| O-09 | 验证器注册表 validators/ | C3-3.8 Harness Engineering | 验证逻辑散落（贯通测试/图表校验/代码审查），反思全靠 LLM 判断 | 新建 `validators/`：统一注册（输入=交付物+标准，输出=通过/失败+证据）；反思自动选适用验证器 | 验证器可在反思与 CI 中复用；同一缺陷证据可复现 |
| O-10 | 反思接受改为评测数据驱动 | C3-3.6 评测驱动开发 | score≥6 即接受，凭经验门槛 | 反思 accept 改为“评测集命中阈值才接受”，评测失败转为 refinery 输入 | 改进前后评测分数可对比，回归不倒退 |
| O-11 | 失败教训结构化写回 | C3-3.8 写回规则 | 反思问题只进 RAG，未写回标准/Skill | 反思失败记录结构化写回对应 Skill 的“改进记录”节（当前只写 overrides.json） | 同一缺陷二次任务不再出现（回归验证） |
| O-12 | 记忆治理 | C3-3.4 持续治理 | MemoryManager 只有存取，无删除/去重/过期/用户界面 | 加 delete/merge/过期策略 + 前端“记忆管理”页（查看/修改/删除）；写准入加“评测达标才沉淀” | 可删除单条记忆；过期记忆自动清理；有用户界面 |
| O-13 | 主动记忆管理 | C3-3.4 agent_control | 记忆注入是被动的 | 反思时让 LLM 输出“记/删/改”结构化操作，orchestrator 执行 | 任务后可查看本轮记忆增删记录 |
| O-14 | Skill 机制与注册表 | C3-3.5 渐进式披露 | 无 Skill 机制 | 新建 `skills/` + 注册表；planner 按 goal 检索 skill description，步骤指令注入 `[Skill: name]`，按需读 SKILL.md（不塞全文） | 命中 skill 的任务自动携带 skill 指引；未命中不受影响 |
| O-15 | 首批 3 个业务 Skill | C3-3.5 | 无 | `research-report`、`game-delivery`、`data-pipeline` 各含 SKILL.md（触发条件/工作流/质量标准/反模式清单） | 每 skill 用对应评测集通过 |
| O-16 | Skills-as-Code | C3-3.5.4 | 无版本/评审/CI | skills/ 进 git；变更走 PR；CI 跑对应评测；YAML frontmatter 加 owner | skill 变更必须过评测才能合入 |
| O-17 | 白盒化评测 | C3-3.6 白盒 | 只有端到端 | 单测 code_execution 生成器、report_generator、content_summary 提取器（固定输入→断言输出结构/指标） | 组件级测试纳入 CI，失败即阻断 |
| O-18 | LLM-as-Judge 校准 | C3-3.6 偏见警示 | judge 直接打分，未校准 | 人工标注黄金测试集→一致性校准（Kappa）；随机打乱候选顺序；每月人工抽检 10% | judge 与人工一致性 ≥0.7；偏见测试样例通过 |

| O-26 | 依赖锁定 | C1 环境标准化 | requirements.txt 未锁版本 | pip-tools 生成 requirements.lock；CI 用锁定版本安装 | 全新环境一次安装成功 |

## 四、执行说明

1. 每项优化完成后，在状态列改为“已完成”并注明版本号与日期。
2. 优先顺序：P0 先行；P1 中 O-05/O-06（评测地基）先于 O-14/O-15（Skill），因为 Skill 需要用评测验证。
3. 所有改动遵循现有代码规范：新增文件走 apply_patch、跑 `python -m unittest test_orchestrator_v2 test_delivery_chain test_common test_prompt_system`、推 GitHub 等 CI 通过。
4. 与 `标准/` 课程的对应关系可追溯：每条优化项的“标准依据”列即课程章节。

## 四十二、修复"结构化数据被静默绕过"：内容注入而非文件提及（2026-08-18）

**用户排查发现（ui-bdf05f3adf）**：financials.json 有东方财富数据，但报告来源全是 IT之家/21财经/雪球，且声称"缺少 2019-2022 及 2025 全年数据"，并出现"净利润主值 1141.15 亿（另有来源称 581 亿）"的假冲突。

**排查结论（逐项核实）**：
- financials.json 里"96 条 2001-2013"是 raw 原文（API 返回全量历史），解析后的 financials 正确（2014-2025，12 份年报）——适配器无 bug；

- "1141.15 vs 581" 是半年报 vs Q1 的不同报告期，冲突检测器不辨期。

| 修复 | 落地 |
|------|------|
| 结构化数据内容注入 | content_summary/report_generator 步骤注入 `[结构化财务数据]` 紧凑年报表（financials.json 最近 12 年 × 营收/净利/毛利率/总负债/经营现金流，含来源名与单位），并附规则：财务数字优先引用本表、来源标注结构化源、表外无法溯源数字标注模型知识 |
