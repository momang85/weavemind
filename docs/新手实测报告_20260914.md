## 二、冷启动实测

### 2.1 引导与配置：可用，但提示端口写死

`start.bat` 六步流程可读性不错（`[1/6] Python` → `[6/6]`），缺 config 时自动进中文引导。用脚本化答案（`WM_WIZARD_ANSWERS`）跑通：

- 选端点 → 填 key（不回显）→ 模型名 → Embedding → **连通性自测 ✓ 连通正常** → 写入 config.json ✓
- 引导结尾提示"下一步：启动后打开 **http://localhost:8080**"，而本次实例实际端口是 8090（`WEB_PORT=8090`）。**端口写死**，多实例/端口被占的用户会被指到错地址。
- 启动完成的横幅同样是写死的：launcher 日志打印 `WebUI: http://localhost:8090`（正确），但紧接着的横幅是 `Ready.  http://localhost:8080`（错）。
- 依赖自检输出清晰：`[OK] Python 3.14 / [OK] 依赖包 14/14 就绪 / [OK] Redis 已运行（localhost:6380，版本 8）/ [OK] 前端产物已就绪（frontend/dist，免 Node）`，末尾 `[OK] 启动校验：16/16 服务存活` ✓ 这一步对新手很友好。

### 2.2 国内网络下的 Redis 获取：**会长时间卡住**（新手第一道坎）

实测（无代理、无法访问 GitHub）：`[4/6] Dependencies` 卡在

```
正在获取便携版 Redis（约 5MB，来自 GitHub releases；国内网络可能较慢或需要代理）…
```

等待 400 秒仍未返回，只能超时中断；最终报错只剩英文兜底提示（`required dependencies are still missing`）。

- 根因：下载源默认是 GitHub releases（`dep_check.REDIS_ZIP_URL`），且校验只允许 https + 公网白名单地址，不能随手换镜像；项目为此留了 `WM_REDIS_ZIP_URL` 但新手不会知道。
- 另一条实测路径（由你提供、我核对）：先把 Redis zip 放到别处（gitee 镜像 / GitHub 加速代理 ghfast.top 均可），解压到 `.weavemind/redis/portable/`，再跑依赖自检即通过（`[OK] Redis 已运行`）。项目文档 §5.1「无 Docker 的完整路径」确实存在，但引导/横幅里没有把它摆在卡住的位置上。
- 建议（低成本、直接改善新手体验）：下载失败时把 `docs/部署指南.md §5.1` 的地址与 `WM_REDIS_ZIP_URL` 用法**打印在同一屏**，并给出"手动放置目录"的确切路径（`.weavemind/redis/portable/`）。

### 2.3 首启的副作用与状态

- `[3/6] Redis` 在本地无 Redis 时自动执行了"Starting Docker Desktop (waiting up to 90s)"，**实际把 Docker Desktop 拉起来了**（事后 `docker version` 变为 server 29.7.2）。对新手是"能跑起来"的好事，但这是一次未经确认的重资源操作，建议提示一句"将启动 Docker Desktop"。
- 首启后 16/16 服务存活；公开 `/api/health` 报 `code_sandbox.mode=docker, isolation_ready=true, execution_available=true` ✓（与本次新加的隔离语义一致）。

### 2.4 **P0 缺陷：创建管理员/登录后页面白屏，必须手动刷新一次**

你反馈的现象，我完整复现并拿到运行时错误：

| 触发动作 | 现象 | 控制台错误 |
|---|---|---|
| 首次「创建管理员并进入」 | 深色空白页（`#root` 子节点数为 0） | `Uncaught Error: Minified React error #300` |
| 「登录」 | 同上 | `Uncaught Error: Minified React error #310` |
| 「退出」 | 同上 | `Uncaught Error: Minified React error #300` |

刷新一次即恢复正常（首帧就已登录，钩子数量一致）。

根因（读码确认）：`frontend/src/App.tsx` 的 `const content = useMemo(...)`（第 103 行）写在 `if (!authed) return <Login />`（第 99-101 行）**之后**。登录态翻转时这次渲染比上次多/少一个 hook，React 抛 #300/#310；而 `ErrorBoundary` 只包住 `content`（第 122 行），**App 之上没有兜底**，于是整棵树被卸载成空白页，用户只看到"黑的"。
影响面：凡是登录态发生变化都会中招——首次创建管理员、日常登录、退出登录；对新手就是"第一步就白屏"。
修复方向（单文件、低风险）：把 `useMemo` 提到早退之前（或直接去掉这个 memo，它依赖数组为空、收益有限）；并修复方向（单文件、低风险）：把 `useMemo` 提到早退之前（或直接去掉这个 memo，它依赖数组为空、收益有限）；并把 `ErrorBoundary` 上提到包住 `Login`，让任何崩溃至少显示"出错了"而不是空白。

**已修（批 F1）**：`App.tsx` 去掉该 `useMemo`、两条分支统一由 `ErrorBoundary` 包裹。浏览器复测：退出（原 #300）与登录（原 #310）两次转换均渲染正常、`errors: []`、`#root` 子节点数为 1，不再白屏。

### 3.1 传奇影业（Legendary Entertainment）— 私营公司，无公开年报 `ui-a372b6834c`

- 7 步、报告 8,194 字、约 9 分钟；中途 `web_search` 失败 1 次（`step_failure.json` 记录 GENERIC_FAILURE + 重试）。
- **诚实度是亮点**：报告开头写明"本次未获取到任何上市公司级别的行情数据；传奇影业为非上市（私募控股）公司"，并列出 5 条检索来源**逐条判定与任务无关（展会资讯、尼日利亚智能家居、南部非洲家庭娱乐、视频游戏收入、孟加拉国娱乐市场）全部剔除**，明确"报告正文不包含任何经检索验证的该公司数值"。
- 验收 `overall=fail`，两条缺口都真实：`交付物不完整：报告含 15 处数据缺失占位`、`数据时效区块缺具体时间`。数字溯源 `total=0`（没提取到数字）→ 覆盖率 0% 但也无数字可查。
- 对金融用户的判断：**该说"查不到"就说"查不到"，方向正确**；但一份 15 处占位的报告无法交付给客户，产品需要把"这家公司没有公开财报"变成一个前置结论 + 替代方案建议（母公司/监管文件/行业估算），而不是让用户在正文里数占位。

### 3.2 华纳兄弟探索（WBD）— 美股上市公司 `ui-15babacb35`

- 9 步（含 `code_execution`）、报告 8,329 字、约 17 分钟；交付 zip + 5 张图 + `make_charts.py`/`render_charts.py`。
- **执行隔离仍无直接证据（此处口径已按架构审查更正）**：`grade=publish` 是**图表质检等级**，不是执行隔离的证明——`charts_pipeline` 的内置渲染脚本走的是**宿主 `subprocess.run`**。要证明"某任务确实在容器里执行"，需要该任务的运行模式、容器执行记录等直接证据；本轮未取到，故记为**待验证**，不能由 `publish` 反推。
- 验收 `overall=fail`，缺口具体：
  - `数字溯源率 8%（3/37）；引用 3 / 计算 0 / 模型知识 18；财务金额溯源率 0%（0/17）；已披露 49% 低于阈值 70%`
  - `三级溯源链：正文引用 5 个编号，来源清单 4 条；缺失引用条目 1 个`
- 报告质量：结构完整（营收结构/净利润/亏损成因/EPS/市值股价/股东结构 + 关键数据一览 + 参考来源 + 免责声明），关键数字**逐条标注**"（基于模型知识，未在本次检索中验证）"，分享页显著位置给出"参考来源 4 个 · 数字可溯源 3/37（8%）· 模型知识已标注 18 处"。
- 但内容实质是**模型记忆**而非检索结果：来源清单只有 1 个东财行情页 + 3 条弱相关新闻；金额溯源率 0% 说明**美股结构化数据链路没有生效**（工作区里没有 `financials.json`，说明 SEC EDGAR/东财结构化适配没接到这条 target 上）。这对金融用户是硬伤：A 股链路此前做到过 85% 溯源，美股链路等于"LLM 凭记忆写研报"。

### 3.3 交付物与运行校验

- 交付 zip、报告 md、图表 png、`chart_data.json` 都在；历史页展开行有 `查看报告` / `重跑` / `验收缺口` 入口（需先展开，属于可发现性小问题，不是缺失）。
- 运行校验（页面上的"贯通测试"）如实报 `2/3 项通过`，其中 ❌ 是：`index.html（html）：页面编码 windows-1252 非 UTF-8（中文会显示为乱码）` —— **系统自己检出了交付物缺陷**（好），但这个缺陷仍进了交付包（该拦没拦）。
- 口径矛盾：历史卡片里徽章是 `SUCCESS_WITH_ISSUES`，同一张卡的"项目交付结果"却写`状态：SUCCESS（8/8 个步骤成功）`。金融用户会困惑"我的报告到底算不算过"。

## 十、补充实测（2026-09-15）：冷启动竞态导致编排器静默死掉

在同一台机器上用相同步骤重建新实例时，出现**首次启动 15/16、编排器未存活**（同一套代码、Redis 已热时重启即 16/16）。

证据链：

- `logs/orchestrator.log` 只有一行（`AgentRegistry initialized`），之后再无输出；
- 用 `faulthandler.dump_traceback_later` 抓到挂起栈：`orchestrator_v2.py:451 OrchestratorV2.__init__` → `common.py:281 MessagingClient.__init__` → `common.py:307 _connect` → `redis ... ping` → **`redis/retry.py:135 call_with_retry`**——即卡在 redis-py 的**重试循环**里；
- `common.MessagingClient._connect()` 建客户端时只设了 `socket_connect_timeout=5 / socket_keepalive / health_check_interval`，**没有关掉 redis-py 的默认重试**（仓库其它模块都已统一加上 `Retry(NoBackoff(), 0)`，并注释说明"默认重试会把超时叠成 26~48 秒"）；
- 冷启动时便携 Redis 刚被拉起、尚未接受连接，于是首次 ping 失败后进入重试风暴：长时间无日志、最终编排器退出 → 新手看到"15/16、提交任务没反应"，且没有任何可行动的提示；
- 反向验证：Redis 已热后重启，`OrchestratorV2 listening on orchestrator:main` 正常打印，15/16 → **16/16**。

影响：这是**新手第一次启动**就会遇到的路径（编排器是任务提交的前置），且失败时没有可读诊断。
建议修法（列入后端批）：① `MessagingClient` 用与其它模块一致的 `Retry(NoBackoff(), 0)` + 明确超时，失败即抛可读异常；② 启动器在拉起服务前**等待一次成功的 Redis PING**（而非固定 `sleep`）；③ 编排器启动失败时，把原因写进启动校验摘要（现在只说"未存活"）。

**已修（后端批首项，2026-09-15）**：① `common.MessagingClient._connect` 传入 `_NO_REDIS_RETRY`——该常量此前在 `common.py:27` 定义了却**零使用**，正是本次静默挂死的直接原因；② `launcher._wait_redis_ready()` 轮询 PING 等 Redis 真正就绪（`WM_REDIS_READY_WAIT` 默认 20s，取代两处固定 `sleep(2)`），超时明确告警；③ 新增 `test_startup_readiness.py`（5 项，已进 CI）：连不通必须数秒内抛错、源码级断言必须传 no-retry、就绪等待的返回值与超时预算、启动路径不得退回固定 sleep。实测 5 项 EXIT=0。
