### 2.1 发现①：共享 token 计数走负 → 配了 `max_tokens` 也拒不了（已修）
`_take_open` 已把预留上界整笔退回（`-U`），`settle` 又按 `(实际−上界)` 记了一遍，实际用量
被扣两次 → 计数一路走负。**修复**：`settle` 只补记实际用量（`+A`）。新增
`TestTokenCounterAccuracy`（计数 = 实际用量 + 未知用量的上界；`max_tokens` 上限仍能拒发）。

### 2.2 发现②：票据 17 vs 调用记录 16（已修）
差额 1 来自 `call()` 的**思考预算重试**分支：它结算票据后 `continue`，但没写调用形状记录
→ 逐条对账时会误以为有一次请求没记账。**修复**：该分支补 `_record_llm_call`
（`end_reason="thinking_budget_retry"`）。

## 3 发现③：待核查指引句被判成"虚假来源标注"（已修）

交付为 `draft` 的唯一原因是验收 `source_labeling` 报"虚假标注 1 条"，命中的句子是：

> 需核查年度报告「合并现金流量表」正文及「财务报表附注—现金流量表补充资料」小节，
> **才能判断**经营现金的**来源是**以销售回款为主还是以其他项目为主…

这是**如实标缺口的指引句**，不是来源声明（`来源是` 被正则当成声明句式）。**修复**：
`_extract_source_claims` 增加整句判据——句内出现"才能判断/需核查/待核查/需核对/无法判断/
不作判断/尚不能/不能据此/需补充/待补充"即**不抽取**。正例仍被抓（`TestSourceLabelingUncertaintyGuard`
三条：指引句不算声明、真虚假标注仍失败、已知来源仍通过）。用存下来的实机正文离线复跑：
`source_labeling` 由 fail → **pass**（不重跑任务、不改门槛）。
