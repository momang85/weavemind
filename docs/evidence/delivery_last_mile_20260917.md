## 二、本轮发现并已修（4 项，都有回归）

1. **交付状态恒为"未知"，最后一公里丢结论**
   验收绑的是报告步骤写出的中间正文（4565 字节 `fail`+4 缺口），收尾把交付说明/评审注记/
   底稿缺口拼成 12184 字节的正文并采纳——两者字节不同，于是交付只能显示
   "该版本没有对应它自身的验收（未知）"。修法：收尾对**被采纳的那份正文**补一次确定性验收
   （幂等；自动修复改写正文时不硬绑，如实留在未知）。
   在真实任务副本上验证：`overall` 由 `''` → `fail`、`本版验收?` 由 `False` → `True`。
2. **`elapsed_sec` 多算 8 小时**：SQLite 的朴素 UTC 串被 `.timestamp()` 按本地时区解释，
   实测"已运行 2 分钟"的任务返回 `28854`。已抽出按 UTC 解析的时间函数；同批把
   "没有 timestamp 的日志推送"落成 UTC ISO（此前落服务器本地裸钟，同一列日志一半本地
   一半 UTC，页面上出现 `59+00:00`、`:14.834Z` 这类残片）。
3. **人工改版不进交付正文**：`review/edit` 只写版本库，页面/导出/PDF 读的是任务 `report`
   字段——接口返回 `ok`，导出的 Markdown 字节与改版前**完全一样**。已改为同步交付正文
   （映射不上就不动，并如实返回 `delivery_updated=false`）；状态与理由统一走
   `verified_delivery`，不再抄"最后一次交付记录"（改版后结论与理由自相矛盾）。
4. **窄屏输入框被压成 24px**：390px 窗口下，输入行的按钮组 `shrink-0` 占 319px，主输入框
   只剩 24px（实际不可输入）。已让按钮组在窄屏独占一行；复测 390px 输入框 345px、
   无横向溢出，1280px 布局不变。

## 三、本轮发现、**未修**（如实挂账）

1. ~~**`identity_id()` 会漂移**~~ —— **已修**（见下）。`bind_acceptance` 会把
   `rules_fingerprint` 覆盖成验收里的值，而身份 = `sha256(version_id|sources|rules)`
   且被当作版本库的键，于是同一版本的"重算身份"与"入库时的键"不再相等（实测：
   入库键 `7faeb4d9…`、重算 `2033fae7…`）。修法：**入库时算出的身份才是权威**
   （`record()` 本来就把它随记录一起写，读取侧只是没用上）——`identity_id()` 对已入库
   记录返回存下来的身份，只有未入库/旧记录才现算；另加 `identity_drifted()` 作为
   "底层字段被回填过"的可审计信号。
   真实任务上验证：`ui-01efce721a` 的 `identity_id()` 由 `2033fae7…` 回到 `7faeb4d9…`，
   与版本库的 `selected` 键一致；页面 `delivery.version_id` 与导出
   `X-Report-Version-Id` 现在都是同一个串（此前对不上任何记录）。
   副作用（正面）：`_key_for` 的身份匹配对已入库记录也终于能精确命中，不再退到
   "按正文 hash 找第一条"。
2. ~~**运行中刷新页面不再跟踪任务**~~ —— **已修**（见下）。运行中重载后后端仍有该任务
   日志，页面日志区是空的（`currentTaskId` 只在内存 store）。做法：把"最后一次提交的
   任务"记进 sessionStorage（按标签页，关标签即清），挂载时若没有在跟踪的任务就查一次
   状态，**未终态**才恢复跟踪（并把顶层 status 补成 running，否则顶栏没有"运行中/停止"）。
   三个边界在实现里定死：只恢复未终态；**明确读到终态才清**恢复点（读不到一律保留）；
   `clearLastTask()` 不放进 `reset()`（`useDemoRunner` 每次非演示模式挂载都会
   `stop()`→`reset()`，放进去会让恢复点被挂载流程立刻抹掉——实测重载后 9 秒内变 null），
   清恢复点改放在"新对话"这个用户主动放弃的路径上；`demo-` 前缀不参与恢复。
   实测：重载后 35 行日志回到页面，顶栏"已运行"与"停止"按钮都在。
3. **文档级数字-主体绑定**缺口（既有挂账，未变）。

## 七、部署烟测（clean-env-e2e）间歇变红的根因与修法

推送后 CI 在 `7338713` 上红了：`backend`/`frontend`/`docker-image` 三个作业通过，
**`clean-env-e2e` 失败**。用 `gh run view --log-failed` 取到日志（不必绕门禁）：

- 失败点是"提交任务"阶段：任务 `RUNNING` → **27 秒后 FAILED**，随后脚本按设计报错退出。
- 同一失败签名**在我这批改动之前就出现过**（`0330b6f`，12:00Z，同样 30 秒内 FAILED、
  同一行报错）——所以不是这批改动引入的，是这道闸门本来就间歇。

在本机隔离环境（独立 Redis 端口 6390，不与你正在跑的应用共用）复现并保留现场后，
从克隆库的 `steps_json` 读到真实链条：

1. 步骤 1 `web_search`（抓 Bing）结果被判不足 → 触发 `Replan (search-fallback)`，
   追加 `code_execution` 步骤（`alt-1-…`）；
2. 该步骤 FAILED，并**替换了步骤 1 的结果**；
3. 步骤 2 `report_generator`、步骤 3 `package` 因此 `Blocked by failed dependency`
   → 0/3 成功 → 任务 FAILED。

也就是说：**部署烟测的成败由外部搜索（Bing）是否返回可解析结果决定**，而 CI 上它间歇失败。
修法是让这道闸门自足：

- `scripts/stub_llm.py` 的替身计划不再排 `web_search`（改 `content_summary`），
  烟测任务的步骤因此全部本地可完成；
- `scripts/e2e_clean_check.py` 的提交目标改为"不需要联网检索"的自足目标，
  并在 `does_not_prove` 里写明"不证明真实检索/抓取链路"。

本地连跑 3 次全部稳定（正向 `SUCCESS_WITH_ISSUES`、负向按预期 `FAILED` 且成功判据拒绝）；
改动前同样的 3 次里有 2 次红。**这不是把闸门调松**：成功判据（夹具标记 + 夹具事实）与
负向用例一条没改，改的只是"不再让外网决定颜色"。

### 该闸门的第二种间歇失败（同一 noche 的后续提交又撞上）

`c9b671d`（仅文档改动）上 `clean-env-e2e` 再次失败，这次是**另一种**模式：任务收执拿到了，
但 `task_history` 在 900 秒里一直不存在（日志里只有重复的"表尚未就绪"），最后按"未在
900s 内进入终态"失败。看不出原因，所以本轮把它变成**失败得快且说得清**：

- 任务库路径**显式钉住**（`WEAVEMIND_DB=<clone>/agents.db`，服务与读取方同一个文件）——
  `db_paths` 的注释里记着历史上"写者读者各读各的环境变量"导致的同类事故；
- 收执后 `LATE_ROW_GRACE=120s` 仍读不到任务行时，把**库路径/文件是否存在/字节数 +
  `logs/{orchestrator,webui,guardian}.log` 尾部**写进日志与证据，下一次失败能直接定位，
  不再是一次"神秘的 15 分钟红"。

本地复跑通过（正向 `SUCCESS_WITH_ISSUES`、负向 `FAILED`）。

### 该闸门的第二种间歇失败：根因已确认并修

上一轮我把它改成"失败时会留下现场"，下一次 CI（`c7eb111`）立刻给出了根因：

```
[e2e] 任务 ui-e74d2f61a1 超过 120s 仍未落库：库=…/clone/agents.db（存在=True，字节=57344）；
      orchestrator.log: 任务 … 终态落库失败（任务库不可写）：no such table: task_history
      orchestrator.log: 任务 … 终态未落库（已尝试 3 次），不标记为已终结：任务库不可写
      webui.log: stale 扫描：崩溃兜底失败：no such table: task_history
```

也就是说：**任务其实跑完了，但写不进库**——库文件存在（agents/sessions/checkpoints 由别的
写入方建了），只缺 `task_history` 这张表。建表此前只由 `web_ui._init_db()` 负责，而任务提交
走 Redis 不经 HTTP：初始化没跑到的进程就只能看着每次写入失败，任务永远停在 RUNNING，
门禁 900 秒超时。这是**产品侧的写库健壮性缺口**，不是门禁挑剔。

修法：让**写入方自己保证表在**——`task_state` 在补列之前先 `CREATE TABLE IF NOT EXISTS
task_history(...)`（基础列与 `web_ui._init_db()` 一致，两边都是 `IF NOT EXISTS`，谁先来都安全）。
新增 3 条回归：空库提交要自建表并落库、空库终态落库要成功、`ensure_schema` 幂等。

## 八、第二次真实公司研究（端点在用，但规划请求失败）

端点诊断（本机、带配置凭据、不回显任何密钥）：

| 请求 | 结果 |
|---|---|
| 端点探针（三个模型名 `qwen3.8-max` / `qwen3.7-max` / `deepseek-flash`） | 均 `ok=True` |
| 规划形状的小请求（max_tokens=2048） | `deepseek-flash` 4.7s、`qwen3.8-max` 9.2s，都返回 JSON |
| 产品里的**真实规划请求**（含注入的历史教训/格式要求，max_tokens=8192） | 两次尝试均失败；任务的降级记录 12 条、末条 `both_failed=true` |

也就是说：不是模型名配错、也不是端点不能用，而是**这个体量的规划请求在该平台上失败**
（主备同域，一起失败）。后果与前一次一致：回退单步 → 没有检索步骤 → 报告零来源 →
验收 `fail`（数字溯源 0/56、引用 0、无来源清单），872 秒收尾，交付如实标未验收草稿。

这次运行同时暴露并已修掉一个"最后一公里"问题（第三节第 1 条的延伸）：

- 收尾把 13302 字节的交付正文送去验收，**验收器的来源标注修复把它改写成 13458 字节的
  诚实披露版**并绑定了那一版；而交付用的还是修复前的正文 → 交付状态显示
  "该版本没有对应它自身的验收（未知）"。
- 修法：**验收器修过的正文就是交付正文**——若被验收的是修复版，就把交付切到它
  （交付与验收对象必须是同一份字节）。真实副本上验证：交付状态由
  `unknown`→`('draft', '验收未通过（overall=fail）')`，交付正文字节 13302→13458。

`identity_id()` 漂移已在本轮修掉（第三节第 1 条）：入库时算出的身份才是权威，
页面/导出/清单与版本库的键现在是同一个串。
