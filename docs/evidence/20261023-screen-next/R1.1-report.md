## 3. 走查中发现并修掉的 4 个不一致（本轮新增，均带测试或截图）

1. **「统一报告期」的标签与预览建议期和实现不是同一件事。** 标签写「全池共同最新年度」、预览写「默认会取 2024年」，实际 uniform 取的是**池内最新可用年度**（真实缓存 + `as_of=2026-10-23` 下是 2025年，三一缺 2025 → 资料不足）。用户会以为默认按 2024年比。已改：标签 →「池内最新可用年度」；`preview.suggested_report_period` 改为与 `evaluate` 同算法（`max(每家最新年度)`），预览与执行永远一致；回归 `test_screen_store.test_suggested_period_matches_uniform_default_not_common_max`（构造「甲有 2025、乙只到 2024」：建议期=2025年=执行 report_period，乙 insufficient 且原因含「不回退」）。
2. **Windows 上 rename 的瞬时失败被当成「历史结果已损坏」。** 走查第一次执行时目标目录不存在、rename 抛 sharing violation，旧逻辑直接按「损坏」回 409，而目录已清掉 → 假损坏。已拆分两种失败：目标已存在 → 复验身份后复用（并发竞争）；目标不存在 → 退避重试 6 次，仍失败抛 `StoreWriteError` → HTTP **503 `store_unavailable`**，明说「没有写入任何结果，可原样重试」。
3. **两条规则的普通用户在 UI 里根本执行不了。** 规则区默认三行，第三行留空时前端把空行原样提交 → 后端 `rules[2] 阈值不是数：''`（后端行为正确，不静默删规则）。已改：前端只丢弃「字段和阈值都为空」的行；填了阈值没选字段仍照发，让后端给明确错误。回归 `test_screen_api.test_blank_rule_row_is_an_explicit_error_not_silently_dropped`（后端不静默删，报 `rules[1] …`）。
4. **历史结果列表看不出每份结果用的是哪一年口径。** 期间政策已进身份与哈希，但列表只有时间/截止日/计数 → 用户要逐份点开才知道「指定 2023年」还是「逐家最新（不可横比）」。已加「期间口径」列（截图 07）。
5. 顺带：执行失败时不再残留上一条「已生成新结果」提示（截图 06）。

## 6. 作用域与数据边界

- `scope` 只能由服务端会话推导：`{user: "admin", project: "personal"}` → `u-8c6976e5b5410415-p-4a0a339b0c6d`。请求体里塞 `{"user":"bob"}` 实测无效（走查第 ④ 段）。
- 隔离实例的持久根：`tmp/r1next-isolated/{agents.db,logs,screen,screen-cache,share,memory}`；真实缓存只读引用，前端产物用 `dist-screen-check`。
- 旧结果仅在 `legacy-runs`/`legacy-presets` 只读保留；本轮 R1 原型实例目录已不在本机，隔离脚本改用**合成 legacy 夹具**（`synthetic:True`，只验证只读/不可采纳/不迁移语义）——证据里明确标注，不冒充历史真实产物。

1. **隔离损坏结果目前只有 API，没有 UI 按钮。** 409 提示里给了 `POST /api/screen/run/quarantine`，但普通用户点不到；这是刻意「难以误触」，但 R1.2 需要补一个二次确认按钮（否则用户遇到损坏只能提工单）。
2. **生产 8080 的重启会引入版本错配**：8080 进程仍是旧代码（`build.restart_required: true`，改动含 `web_ui.py`），`frontend/dist` 是 2026-10-22 23:39:35 且不含本页 chunk。重启 + 不重建前端 = 新 API 配旧前端。需要「同版本重建 + 前端/后端一起回滚」的清单，本批不做。
3. **真实缓存只有 2 家公司、1 个截止日剖面**，所有「通过/未通过」都是两点样本，不能当市场样本或策略效果。
4. 期间政策目前只到「年度」标签粒度；半年度/季度、重述版本并存的口径未处理（属 R2 数据缺口议题）。
5. 未做并发写压测（同一身份两个进程同时写只做了代码级复验 + rename 竞争分支），建议 R1.2 加一个多进程同写用例。
