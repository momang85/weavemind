## 3. 本次修掉的三个真问题

### 3.1 两个实例共用一台 Redis → 任务被另一个实例抢去执行（最严重）

**现象**：我在 8081（运行包实例）提交的任务，被 **8080（开发实例）的编排器**抢走执行；
开发实例那把密钥余额不足，于是把这条任务标成 FAILED，而运行包实例仍在跑同一条任务。
两个实例的库里都有这条任务，页面显示的状态是两份的混合。

**机制**：`web_ui` 用 Redis **pub/sub** 在 `orchestrator:main` 频道投递任务，
而每个编排器进程都订阅该频道——pub/sub 是广播，**每个订阅者都收到每条任务**。
默认端口上又是"复用兼容 Redis"，于是同机两个实例共用同一总线。

**修复**（`launcher._portable_redis_owned_here` + `_ensure_redis_available`）：
默认端口上的 Redis **若不是本实例启动的**（本实例的 `runtime_ports.json` 端口 + `.weavimind/redis.pid`
都对不上），就不复用，本实例另起自己的便携 Redis 于空闲端口。
显式配置的 Redis（自装 Memurai／远端）照旧复用——那是用户的选择。
实测：开发实例保持 6379，运行包实例自起 6380，任务不再串台。

**未修的部分（如实）**：如果用户**显式**把两个实例都指向同一台 Redis，pub/sub 仍会广播，
任务仍会串台。频道名加实例命名空间是更彻底的修法，涉及 web_ui/编排器/worker/guardian 多处
频道名，未在本批做。

### 3.2 模板里的角色/规划/备用端点 → 首次任务的评审直接降级

**现象**：`critic: 评审返回 DEGRADED：评审系统不可用（评审调用失败: LLM call failed after 2 attempts）`，
报告因此带"评审未完成（降级）…须经人工复核"。

**机制**：随包模板 `config.example.json` 里 `model_roles` 写死 `deepseek-chat`（该端点并不提供）、
`planner`/`backup` 段写死另一家厂商地址 + 占位密钥。设置页只让用户填主端点与主模型，
这些模板值就原样生效：规划/评审打到一个不存在的模型与一个不存在的端点。
日志可见 `LLMClient: model=deepseek-ai/DeepSeek-V3, base_url=https://api.siliconflow.cn/v1`。

**修复**：模板的 `model_roles` 三项与 `planner`/`backup` 的地址、密钥一律留空
（缺省跟随主模型/主端点，符合 N3"首次默认角色映射与该服务一致"），
并给 `planner`/`backup` 加占位符守卫（占位符不得注入环境变量、不得当备用端点）。
验证：新手只填主端点后，`plan/exec/judge` 三个用途全部解析到主模型，无备用端点、无幽灵规划端点。

### 3.3 配置缺失时回退到硬编码 stub → 新手实例丢了产品默认值

**现象**：新手实例日志 `评审未完成（降级，个人模式继续）：critic 已关闭（system.critic=false）`；
设置页显示任务超时 90 秒、任务预算 0（=不限）。

**机制**：`web_ui._load_config()` 在 `config.json` 不存在时回退到一个**硬编码最小 stub**，
而源码方式是把 `config.example.json` 复制成 `config.json`——两种方式的默认值因此不一致，
模板里的 `system.critic=true`、`task_timeout=300`、`task_budget 60/1800` 在新手实例上全部失效。

**修复**：回退改为随包模板；同时补"占位符不算已配置"（`setup_wizard.looks_placeholder` 公开入口
+ `web_ui._llm_config_complete` + `launcher._config_looks_placeholder`），
否则模板里的 `YOUR_API_KEY` 会让首启引导误判"配置完整"而隐藏。
实测：修复后新手实例拿到 `task_timeout=300`、`task_budget 60/1800`、**评审已启用**。
